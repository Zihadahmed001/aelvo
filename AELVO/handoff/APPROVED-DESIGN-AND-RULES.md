## User-approved revised requirement: signup and checkout phone OTP
The user's clarification on 6 October supersedes the earlier rule requiring a fresh OTP for every checkout. Account creation requires successful mobile-number OTP verification. A signed-in customer ordering with that same verified account number does not receive another checkout OTP. A different order contact number must be verified for that checkout. Guest checkout remains supported and requires OTP verification; it must not force account creation.

| Situation | Required behavior |
| --- | --- |
| Create a new account | Verify the signup number before creating or activating a usable account. |
| Signed in, order number matches the current verified account number | Show Verified and continue without a new OTP. |
| Signed in, order number differs from the verified account number | Verify the different number before payment/order placement. |
| Guest checkout | Verify the order number, even if it happens to belong to an existing verified account. |
| Change an order number after verification | Re-evaluate the new number; the prior number's checkout verification does not transfer. Returning to the signed-in customer's own verified number may use the matching-account rule. |
| Change the account's primary phone | Verify the proposed new number before making it the verified account number. |

Verifying an alternative delivery/contact number for an order must not silently change the account's primary phone or attach another person's order/account history. A phone match alone never authenticates a guest or grants account access.

Implementation requirements to carry into architecture and acceptance testing:
- Normalize numbers consistently before comparison. Persist verified account-number status server-side; bind guest/alternative-number OTP verification to the exact number and current checkout. Do not trust browser-only verified flags or an unrelated account's verified phone.
- Enforce the rule on every public order-placement route, including direct requests. Skip a new OTP only when an authenticated customer's submitted order number exactly matches their current verified account number, or when valid verification for that number already exists in the current checkout.
- Verify the contact number before starting a required advance-payment flow; keep the verified checkout association through the payment handoff.
- Use short-lived single-use codes, attempt limits, resend cooldowns, and send/verification rate limits. Final values and the SMS provider remain implementation decisions.
- Permit paste and SMS autofill where supported. Show masked destination, Change number, resend countdown, invalid/expired-code feedback, and verified state.
- Expired, exhausted, or superseded codes cannot verify signup or checkout. Replaying an already used code or callback must not create another account or order.
- Log safe verification events without recording OTP plaintext. Keep provider credentials server-side and avoid exposing whether a phone belongs to an existing customer.
- SMS failures must offer a clear retry path and preserve the cart; do not silently accept an unverified order.
- Phone verification confirms access to a number. It reduces wrong-number and some fake-order attempts; it is not proof that the buyer will accept delivery. Retain the existing customer-risk and fraud-review requirements.
