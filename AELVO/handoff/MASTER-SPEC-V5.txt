Editable fields:

• Default social sharing image

30.5 BRAND SEO

30.6 CMS AND HOMEPAGE SEO

Homepage SEO has its own editor for SEO title, meta description, canonical, sharing image and applicable structured data settings.
Keep the homepage route fixed at the site root. A generic slug control must not accidentally move or duplicate it.
Do not force homepage metadata to use hard-coded branding or promotional text.

30.7 URLS, SLUGS AND ROUTE OWNERSHIP

Use clean, readable URLs without unnecessary IDs or query strings. Necessary pagination and filter parameters remain supported.
Validate slug normalization, length, Unicode handling, reserved routes and collisions across all content types sharing a namespace.
Use a database unique constraint on normalized public paths, with friendly validation errors and transaction-safe conflict handling.
Reserve admin, account, cart, checkout, search, install, API, assets, robots.txt, sitemap and verification routes.
Decide lowercase, trailing-slash and HTTPS/hostname rules once; consistently use them in links, canonicals, redirects, OG URLs and sitemaps.

A slug change must atomically update route ownership and create a 301 from the old public route.
Refresh internal links, breadcrumbs, schema URLs, sitemap entries and metadata caches.
Category-parent changes must account for descendant routes if nested paths are chosen.
Do not release historical redirect paths for conflicting content accidentally.

30.8 REDIRECT MANAGEMENT

Admin → SEO → Redirects supports create, edit, disable and review.
Store old path/URL, destination URL, HTTP type (301 or 302), enabled status, created/updated timestamps and responsible user.
Record whether generated automatically from a slug change or created manually.
Use 301 for permanent route changes; use 302 only for intentional temporary redirection.

Prevent self-redirects, cycles, duplicate active source rules and conflicting live routes.
Check the entire redirect graph on changes, including previously disabled rules when re-enabled.
Update historical redirects to the latest destination to avoid unnecessary chains.
Default destinations to the same approved website. External destinations require an explicit validated host policy; reject unsafe schemes and malformed URLs.
Define query-string handling explicitly; never blindly append sensitive parameters to destination URLs.
Do not use unrestricted regular expressions for the initial redirect manager.
Show broken, inaccessible or non-final destinations as warnings without automatically deleting rules.
If performing remote destination checks, restrict allowed hosts and prevent requests to private/internal networks.

30.9 XML SITEMAPS

Serve /sitemap.xml and automatically include eligible products, categories/subcategories, brands and CMS pages, including the homepage.
Only include published, public, indexable, canonical URLs that resolve successfully.
Exclude admin, account, cart, checkout, internal search, unpublished content, noindex pages, redirects, errors, noncanonical variants and ordinary filter/sort URLs.
Use absolute URLs, UTF-8, correct XML escaping and accurate lastmod values reflecting substantive changes.
Do not reset every lastmod on every request.
Support sitemap indexes and split files before either 50,000 URLs or 50 MB uncompressed is exceeded.

Regenerate/invalidate on publish/unpublish, relevant content changes, slug changes, canonical/indexing changes and removal.
Use bounded database queries and atomic publication so visitors never receive a half-written XML file.
Support cPanel deployment without mandatory command-line setup or a permanent queue worker.
Use cached generation/invalidation with an authorized rebuild action; optionally support cPanel cron for larger catalogs.
Show last successful generation, URL count, exclusions, errors and the submission URL in Admin.
Do not claim that sitemap inclusion guarantees crawling or indexing.

30.10 ROBOTS.TXT AND INDEXING

Serve a safe root /robots.txt with an absolute Sitemap directive.
Allow authorized users to configure crawl rules through a validated editor and preview affected representative URLs.
Warn clearly before publishing rules that block all public content, required assets or important categories/products.
Do not accidentally carry development/staging disallow-all or sitewide noindex into production.
Protect staging with access control; provide a launch review of effective indexing settings.

robots.txt controls crawling; it is neither access control nor a reliable method of removing URLs from search results.
Use authentication/authorization for private pages, noindex on appropriate reachable HTML pages, and X-Robots-Tag where appropriate for non-HTML responses.
Do not expose private paths or documents on the assumption robots.txt protects them.
Do not write an unsupported noindex directive into robots.txt.
When a crawler must see a page's noindex or canonical, do not block that page in robots.txt.
Document any later crawl-blocking policy separately from deindexing and verify its intended effect before deployment.

30.11 CANONICAL, FILTER, SEARCH AND PAGINATION POLICY

Produce one effective canonical on applicable HTML pages, using absolute URLs.
Validate overrides and warn about destinations that redirect, return errors, are noindex, are unrelated, or conflict with sitemap/internal-link policy.
Never canonicalize all categories, filtered pages or pagination pages indiscriminately to the homepage.
Canonical annotations are search-engine signals, not guaranteed directives.

Proposed policy for Feature Review, to be implemented and tested before deployment:

• Normal product/category/brand/CMS pages: self-canonical and indexable unless deliberately configured otherwise.
• Equivalent campaign/tracking URLs: canonical to the clean equivalent, preserving meaningful content and pagination parameters.
• Duplicate product paths: preferably 301 to the selected primary route; otherwise use the same canonical and consistent internal links.
• Category pagination: each valid page has its own canonical, e.g. /men/shoes?page=2. Do not canonicalize all pages to page 1. Normalize ?page=1 to the base URL. Use real crawlable <a href> links; load-more/infinite-scroll may enhance these links but must not replace discovery.
• Out-of-range/nonexistent pagination and invalid filter combinations: return an appropriate real 404, not an unlimited series of empty 200 pages.
• Ordinary filter combinations that produce different subsets: default noindex,follow; omit cross-page canonical consolidation rather than incorrectly treating every subset as identical to its parent. Exclude these URLs from sitemaps. Keep them crawlable while relying on noindex.
• Alternative sort orders: default noindex,follow and exclude from sitemaps; avoid a blanket canonical to an unrelated unfiltered/paginated product set. Choose a canonical-only approach solely for verified equivalent representations, documented in the route policy.
• Selected valuable filter landing pages: only explicitly approved pages with useful unique content, stable clean routes and curated internal links may become indexable/self-canonical. Do not auto-generate thousands of indexable combinations.
• Internal search (/search?q=shoe): noindex,follow and no sitemap inclusion. Normalize/limit parameters and avoid publishing unlimited crawlable query links. Do not depend on search results for product discovery.
• Simple selectable variant URLs: canonical to the parent only when they represent substantially the same product page. If distinct indexable variant landing pages are approved, use a separate documented canonical/variant-schema strategy. Selection, displayed price, stock and schema must agree.

Review crawl logs and URL inventory before adding broader facet/search robots blocks. Do not combine those blocks with a promise that crawlers will read the blocked pages' noindex.
Maintain product discovery through ordinary indexable categories and sitemaps, even where noindex pages exist.
Provide concrete URL examples and expected status/canonical/robots/sitemap outcomes in the deployment checklist.

30.12 STRUCTURED DATA

Generate valid JSON-LD from actual database content through reusable schema builders.
Support Organization, WebSite, BreadcrumbList, Product and Offer on appropriate pages.
Support Review/AggregateRating only when real, published reviews exist and are visible to customers.
Support FAQPage for eligible visible FAQ content where applicable; do not promise Google FAQ rich results for an ordinary fashion store.
Prepare an Article/BlogPosting extension point without building a full blog before Feature Review approval.

Product data may include actual name, images, description, SKU, brand, price, currency, availability, canonical product URL, rating and review count.
Use the real store currency (BDT when configured), numeric prices and appropriate availability values.
Use real offer dates and identifiers only when available; never invent GTINs, reviews or rating counts.
Keep schema price/availability synchronized with the visible page and transactional data, including variant selection and promotions.
Invalidate affected caches after price, stock, review or product-status changes.
Encode JSON safely rather than concatenating raw user input into script elements.
Only emit schema appropriate to the page's visible content; no Product schema on unrelated pages.
Validate with relevant schema tools/Rich Results Test where supported. Passing validation does not guarantee a rich result.

30.13 BREADCRUMBS AND INTERNAL LINKS

Provide visible, accessible, crawlable breadcrumbs, e.g. Home → Men → Shoes → Sneakers → Product.
Generate consistent BreadcrumbList JSON-LD from the same hierarchy.
When a product belongs to several categories, choose a stable primary breadcrumb hierarchy.
Navigation, category pages, related products and breadcrumbs must link to the current canonical public paths.
Avoid orphan products and links that depend entirely on JavaScript click handlers.

30.14 SOCIAL SHARING

Render og:title, og:description, og:image, og:url and appropriate og:type; include site name and applicable image dimensions/ALT information.
Support Twitter/X card metadata with per-page fallbacks to the page's SEO and global defaults.
Use public absolute HTTPS URLs for images and pages.
Provide metadata suitable for compatible Facebook, Messenger, WhatsApp, LinkedIn and other sharing consumers.
Explain that preview rendering and cache refresh depend on each platform; identical appearance everywhere cannot be guaranteed.

30.15 IMAGE SEO AND DELIVERY

Every meaningful product image supports editable ALT text and sensible generated defaults, with optional image title where useful.
Use descriptive filenames where practical while retaining server-generated uniqueness and secure upload validation.
Provide width/height or stable aspect ratios, responsive image sizes/srcset, compression and suitable modern formats with fallbacks where needed.
Lazy-load appropriate below-the-fold images. Do not lazy-load the main above-the-fold product/hero image when it is the likely largest visible element.
Decorative images use empty ALT text; do not keyword-stuff meaningful image descriptions.
Keep image replacements and generated thumbnails synchronized with metadata and schema references.

30.16 INDEXING AND DISCONTINUED PRODUCTS

Authorized admins can select index/noindex and follow/nofollow for every supported content type.
Resolve defaults consistently and show the effective result, including any global noindex override.
Publishing a page must not silently override an intentional noindex setting.

Discontinued products must not be automatically deleted.
Admin chooses the appropriate behavior:
• Keep a useful 200 page with a clear Discontinued status and alternative products.
• Keep it live but noindex.
• 301 to a genuinely relevant replacement where appropriate.
• Permanently remove with an appropriate 404/410 when appropriate.
Temporary out-of-stock products normally remain accessible with truthful availability.
Do not mass-redirect missing products to the homepage or irrelevant categories.
Update sitemap membership, internal links, schema and caches after the selected change.

30.17 SEO AND SOCIAL PREVIEWS

Show a Google-style search preview: effective page title, public URL and meta description.
Show a social share preview where practical, including fallback images and text.
Display title/description length guidance and truncation warnings, but never block a valid save solely because of length.
Preview text is illustrative; Google and sharing platforms may choose different titles, descriptions or crops.

30.18 SEO WARNINGS

30.26 ACCEPTANCE CRITERIA AND RELEASE GATE

SEO is not complete until verified against actual application responses and permissions:
1. All supported entities and homepage expose persisted authorized overrides and sensible empty-field fallbacks.
2. Raw server HTML has correct effective title, description, canonical, robots, OG/Twitter tags and page-appropriate factual JSON-LD without duplicate/conflicting tags.
3. Slug changes create correct 301s; repeated changes resolve without loops or unnecessary chains; concurrent collisions are rejected safely.
4. Sitemaps contain only eligible current canonical URLs and update after publish, slug, canonical/indexing and removal changes. Verify XML parsing, URL escaping and splitting boundaries.
5. Representative filter, sort, campaign, variant, search and paginated URLs produce the approved status/canonical/robots/sitemap behavior.
6. Page 2 and later remain discoverable by ordinary links and are not mistakenly canonicalized to page 1.
7. robots.txt does not prevent crawlers from seeing relied-upon noindex rules or block essential public content/assets.
8. A nonexistent URL returns a real 404; discontinued product actions follow the saved policy and truthful availability.
9. Product schema prices, currency, stock and real review counts match visible content after cache invalidation.
10. Ordinary employees cannot edit SEO through direct requests; authorized changes produce audit records.
11. Malicious metadata, JSON-LD strings, redirect URLs, upload names and verification input cannot execute code or escape validation.
12. Mobile layouts, image ALT/dimensions, initial HTML content and performance are checked on representative home, listing and product pages.
13. Disabled integrations do not load; enabled integrations use configured IDs and do not duplicate events.
14. Production uses the correct HTTPS domain and approved indexing settings, with no accidental localhost/staging canonicals.
15. README includes SEO operations, sitemap submission, slug/redirect behavior, robots/noindex distinctions, verification setup and recovery guidance.

Record failures and fixes; do not label a visual mockup, specification or unconnected admin form as implemented functionality.
No keyword stuffing, hidden text, cloaking, fake reviews, spam pages or guaranteed-ranking promises.
